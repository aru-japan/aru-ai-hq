1. 設計方針

法改正も、イベントも、日本文化も、旅行情報も — 公開される時点ではすべて「記事」という一つの型に収斂する。

取材・翻訳・SNS展開・人的レビューといった編集部の裏側の作業は、それぞれ専門構造を持つ独立したデータベースが担う。両者はリレーションで接続され、「記事」だけが唯一の公開レイヤーとなる。

原則： 記事DBは1つ。支援DBは役割ごとに分ける。すべての支援DBは、直接または間接に記事DBへ接続する。ダッシュボードだけが例外で、他の全DBを読み取るだけの「報告レイヤー」。

3. 記事DB（コア・唯一の公開DB・日本語マスター）

Article 記事（日本語マスター）
Public / Core / Parent

法改正・イベント・日本文化・旅行情報・生活情報・ニュース — すべてのカテゴリがここに集約される唯一の公開コンテンツDB。レコードは常に日本語1本のみ。他言語は複製せず、子DBのTranslationが1記事につきN件ぶら下がる構造にする。

プロパティ型説明
TitleText記事タイトル（日本語）
CategorySelect法律・制度／イベント／日本文化／旅行情報／生活情報／ニュース／トレンド
Target AudienceMulti-select旅行者／在留外国人／留学生／技能実習・特定技能／移住希望者／企業／自治体／日本語学校
BodyRich Text本文（日本語）
Master StatusSelectDraft → AI Draft → Human Review → Approved → Published → Archived（日本語本体の進行状況）
Publish Date / Update DateDate日本語版の公開日・更新日。Update Dateの変化がTranslation側の「要再翻訳」判定の起点
Source ResearchRelation → Research出典（イベント・観光・文化など一般カテゴリの場合）
Source Law UpdateRelation → Law Update出典（法律・制度カテゴリの場合）
Source EventRelation → Event Calendar出典（イベント情報カテゴリの場合）
Law SignificanceRollup ← Source Law Update.Significance紐づくLaw Updateが「重要な変更」かどうかを引き継ぐ

6. 自動化ワークフロー（n8n連携を見据えて）

Source更新からTranslation生成・公開までを一本のパイプラインとして自動化する。人が介在するかどうかの分岐点は、Update Levelの1点に集約される。

  1. Source更新検知 — Source Library内の政府サイト・自治体RSS・ニュースAPIの変化を、Automationが定期的にチェックする。
  2. Research更新 — 変化が検知されたSourceをもとに、AI（Research Agent）がResearchレコードを新規作成、または既存レコードを更新する。
  3. Article更新 — 採用されたResearchから、AI（Writer Agent）が日本語Articleを生成・更新する。既存記事の更新では Update Date が変わり、紐づく全Translationの Needs Re-Translation が自動的に再評価される。
  4. Update Level判定 — CategoryとLaw Significanceから Update Level（1／2／3）が自動算出される。
  5. Translation自動生成 — Needs Re-Translation = Yes の各Translationに対し、AI（Translator Agent）が翻訳を実行し、AI Translation Status を Done にする。
  6. レベル別の公開フロー — 下表の通り分岐する。
  7. SNS展開 — Publish Status が「公開」になったArticle／TranslationをSNS Queueへ自動登録し、AI（SNS Agent）が投稿文を生成する。
Level対象カテゴリ人のレビュー公開承認通知
Level 1 イベント情報／観光情報／飲食店情報／文化紹介／季節情報／旅行記事 不要 不要（自動公開） なし
Level 2 法律／行政手続き／ビザ／税金／年金／保険／医療／教育制度／労働関係 必要（担当Reviewer） 必要 Reviewerへレビュー依頼通知
Level 3 上記のうち Law Update.Significance = Major な重要更新 必要（編集長／専門メンター・優先） 必要（Approved Dateを記録） Change Summary添付の優先通知

7. 拡張性メモ（数万記事・多言語・企業向け展開）

  • Notionの限界を織り込む。 Notion DBは数千〜1万件を超えるあたりからRelation/Rollupの表示速度が落ちる。「数万件の記事」規模になった段階で、Article／Translationの実データはPostgres／Supabase等へ移し、Notionは編集部の作業画面（API経由のビュー）として残す2段階移行を前提に設計しておくと、10年後の作り直しを避けられる。特にTranslationは12言語×記事数で最も件数が膨らむDBになる点に注意。
  • Language Masterが20言語以上への拡張を支える。 言語をArticle/TranslationのSelect肢として直接埋め込まず、独立DBにしたことで、新言語追加は「1行足すだけ」になり、スキーマ変更・過去データの一括移行が発生しない。
  • Tenant（テナント）概念を今のうちに仕込む。 将来の企業向け展開に備え、ArticleとMentor DBに「Tenant / Client」フィールドを最初から用意しておく。後から追加すると全レコードの移行作業が発生するため、空でよいので今から列だけ確保する。
  • Needs Re-Translationが「翻訳の負債化」を防ぐ。 日本語記事を更新しても翻訳側が自動では変わらない設計だと、時間とともに「古い翻訳」が静かに蓄積する。Article.Update DateとTranslation.Last Source Checkの差分で「要再翻訳」を自動検知する仕組みを、Automationの最優先ワークフローの一つとして早期に組む価値がある。
  • Update Levelの算出はArticle側で一度だけ行う。 Category（＋Law Significance）から算出し、Translationは常にRollupで受け取るだけにする。レベル判定ロジックを複数箇所に重複させないための設計上の一貫性。
  • Status列はAutomationのトリガーキーになる。 Article.Master Status、Translation.AI Translation Status／Human Review Status／Publish Approvalは、n8nが「次に何をするか」を判断する軸になる。ステータス名は今後変更しにくいので、早い段階で確定させたい。
